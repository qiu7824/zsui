# ZSUI 内存与稳定性优化计划

## 目标与基线

在保持原生文字、输入、无障碍和防闪烁行为的条件下，减少重复持有的文字、
排版和字体数据，降低常用页面及多窗口的私有内存，并用重复运行证明资源
生命周期稳定。各阶段独立提交、独立测量，未达到收益与正确性门槛的候选
不进入默认实现。

代码基线固定为 `91cda3bb9b362c42276b5508eb2f79cf0d8ce991`。它已包含直接
借用 Windows 绘制缓冲及隐藏窗口释放缓存的优化。下一阶段只能报告相对
这条基线的新增收益，不能再次计入此前已取得的下降。

已发布的 `0.3.0-alpha.2` 作为独立发布对照，不能与上述代码基线混用。
候选版本号在 API 兼容性审查后确定。所有数据均记录源码内容标识、工具链、
目标架构、features、构建参数、字体环境和二进制哈希。

## 验收指标

以下数值是工程目标与准入规则，不是尚未测量的性能预测。

| 维度 | 指标与门槛 |
| --- | --- |
| 单窗口内存目标 | 在文字密集页面和 Common 表单中，争取稳态私有内存中位数各降低至少 10%，且每个场景至少节省 512 KiB |
| 多窗口内存目标 | 同一进程三个窗口的私有内存中位数降低至少 15%，同时确认共享资源不被单个窗口关闭或隐藏提前释放 |
| 其他场景保护 | 同平台其他场景的私有内存、隐藏内存和峰值不得出现超过 `max(3%, 256 KiB)` 的可重复增加 |
| 延迟保护 | 暖启动、恢复窗口、输入到显示及滚动帧耗时的 p95，不得出现超过 `max(5%, 1 ms)` 的可重复退化；同时报告绝对值 |
| 空闲 CPU | 不增加持续轮询；超过基线 0.1 个整机 CPU 百分点的可重复上升需要定位并解决 |
| 资源回收 | 完成预热后，100 次创建/关闭和 200 次隐藏/恢复不出现持续增长；最终静置后的私有内存相对首个暖态检查点增量不超过 `max(3%, 512 KiB)` |
| 原生资源 | 无本次创建且未释放的窗口、线程、GDI/USER 句柄；进程级后台资源须能解释其固定数量与生命周期 |
| 功能正确性 | 无新增文字、布局、IME、焦点、选择、滚动、无障碍和窗口生命周期回归；原有已知差异单独列账 |
| 可恢复性 | 任一阶段可单独撤回；应用状态、公共稳定 API 和现有功能裁剪契约保持可用 |

Windows 以 Private Bytes 为主要内存指标，并单列工作集、峰值和缓存容量。
Linux 单列 Private RSS、PSS、RSS；macOS 单列 physical footprint 和 RSS。
不同操作系统指标不直接做数值排名。跨平台公共改动在各目标系统分别验证。

## 实施阶段

| 阶段 | 工作与产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| G0：可信基线 | 修复或定位现有测量链路问题；补齐逐次可见性确认、运行身份、输入完成确认及逐轮采样；建立可复现基线报告 | 同一代码可重复运行，必要目标验证通过，失败与取消均已解释 |
| G1：文字数据去重 | 梳理节点、绘制计划、排版键和无障碍之间的文字副本；采用短期借用或不可变共享记录；测量布局元数据与字形数组占用 | 复制和分配减少，文字编辑及旧快照生命周期正确，至少一个目标场景具有可重复收益 |
| G2：字体与 TextContext 拆分 | 共享有明确所有者的只读字体数据；可变排版和光栅缓存保留明确线程归属；先保留必要同步，再评估锁范围 | 三窗口与混合 DPI 测试通过，隐藏/销毁/UIA 查询互不破坏，满足多窗口收益目标 |
| G3：按证据试验字形图集 | 对比现有独立位图缓存与有上限的分页存储；包含彩色字形、大字形、碎片、元数据和淘汰开销 | 总内存及帧耗时实测支持替换，完整键与失效代数检查通过；否则保留现有缓存 |
| G4：按证据试验脏区域 | 先验证布局/绘制失效传播，再增加局部重绘；保留整帧缓冲和原有完整重绘恢复路径 | 滚动、遮挡、透明、阴影、缩放和快速尺寸变化无残影、漏画、闪烁，CPU/耗时确有收益 |
| G5：按证据试验 arena | 分开 Element 身份/状态与 RenderObject 几何；评估连续存储、稀疏状态和带代数句柄 | 节点内存与遍历成为已证实瓶颈，收益覆盖额外复杂度，旧 ID 与闭包生命周期回归通过 |

下一验证版的必做范围为 G0、G1、G2。G3—G5 是受数据约束的后续实验，
不要求同时替换全部架构。紧凑排版从 G1 的去重与按段共享属性开始；压缩
坐标和裁减字形字段必须保留准确塑形、字体回退、双向文本及光标语义。

共享不等于增加进程级可变控件注册表。字体映射必须由实际对象持有，不能
制造虚假的 `'static` 生命周期。UIA 跨线程查询采用安全快照或有明确顺序的
同步协议；不得在持有绘制锁时等待会重新进入绘制的原生回调。

## 对照测试方法

1. 使用同一机器、操作系统、字体、DPI、窗口尺寸、数据、release 配置及
   Cargo features。基线和候选各保留一份对应产物，共用兼容的稳定构建缓存。
2. 在同一平台交替运行基线和候选，至少完成 10 对独立进程；平衡先后顺序。
   每进程固定预热时间后，每阶段采集至少 20 次样本。
3. 以每进程的中位数作为独立观察值，报告成对差值与 95% 置信区间；
   同一进程内的多次采样不当作多次独立实验。区间不能支持明确收益时，
   结果记为“尚未确认”，不能只选最低一次。
4. 样本同时确认进程创建时间、窗口可见/隐藏状态和目标操作已完成。
   发现意外输入、失焦、PID 重用或缺失截图时，记录剔除原因并补跑配对样本。
5. 测量可见、隐藏、恢复、关闭后的静置阶段，并记录全过程峰值。禁用主动
   工作集裁剪；固定功能和视觉质量，不以关闭断言、缩小数据或降低文字质量省内存。
6. 延迟场景每轮至少采集 200 次已完成操作，分别统计输入、滚动和恢复；
   短场景内存采样与延迟压力测试分开，避免测试工具本身改变目标负载。

| 工作负载 | 覆盖内容 |
| --- | --- |
| Minimal / Common / Full Native App | 沿用现有性能矩阵，正式应用不加入 Viewer 或 proof 功能 |
| Viewer | 独立开发工具行；文档重载、稳定 ID、输入状态保持 |
| Panel / Large text | 沿用内存生命周期样例和固定多语言内容，便于连接已有基线 |
| 多窗口 | 同进程 1、3 个窗口；相同及不同文字；100%、150%、200% DPI；任意窗口关闭和隐藏 |
| 持续编辑 | 中文、拉丁、阿拉伯文、希伯来文、emoji；选择、IME、撤销、缩放及长文本换行 |
| 动态节点 | 反复增加、删除、重排节点，保持焦点和稳定 ID；查询旧节点或旧文字范围 |
| 长时循环 | 30 分钟固定操作循环，加创建/关闭及隐藏/恢复循环；观察增长斜率和资源所有者 |

长时测试按固定次数执行，不建立后台监控或定时任务。私有内存达到平台后
仍需核对句柄与资源计数；“未崩溃”不能单独作为无泄漏证据。

## 稳定性证明

为每个已确认问题保存“触发条件—基线失败—候选通过”的回归用例。新增
生命周期用例覆盖旧排版快照存活、字体共享者先后退出、缓存淘汰后绘制、
代数复用、并发 UIA 查询与销毁、隐藏期间命令送达及恢复后的状态一致性。

固定表面截图保持一致；动画与失效测试还需逐帧或事件序列证据。既有字体
oracle 的五个加权 emoji/混排差异继续单列，不因内存下降删除失败样本。
Miri 或其他内存检查仅用于适用的纯 Rust 核心，不能替代 Win32/AppKit/Linux
目标机验证。

必需检查包含格式、无默认特性测试、full 测试、locked feature matrix、
文字 oracle、原生交互与无障碍。修改公共跨平台数据结构时补齐三个桌面
平台的运行证据；编译通过不代表对应平台完成。

“问题更少”仅在已复现问题被消除、回归集合扩大且没有新增阻断问题时成立。
未发现错误与已消除错误分别报告。

## 当前前置问题

截至 2026-10-26，基线普通 CI、UI Memory Comparison、DataViewer、ARM64、
Stable API/Rustdoc 已通过。以下两项进入 G0：

- [macOS 性能矩阵](https://github.com/qiu7824/zsui/actions/runs/40291510456)
  在 Minimal 场景隐藏进程时出现 `NSRunningApplication rejected hide`。
  Ubuntu 矩阵通过。应定位隐藏状态、宿主响应和测量脚本的行为，不把失败
  直接归因为内存改动，也不跳过隐藏阶段制造完整结果。
- [Native UI Proof](https://github.com/qiu7824/zsui/actions/runs/40291510524)
  的 Win32、AppKit、Wayland 作业通过；Linux 作业在 GTK4 Notepad 文件对话框
  步骤被取消，上传步骤失败。取消原因和该路径的最终结果尚需确认。

## 决策与交付

每阶段交付源码提交、正确性报告、同条件前后数据及回退点。公开报告保留
正式结论、数值和适用范围；临时日志、运行记录与预览存放于操作目录。

- 收益达标且所有保护条件通过：纳入下一候选版本。
- 有局部收益但整体目标未达标：保留可独立成立的修改，报告准确范围。
- 收益不足、引入回归或证据不足：不替换默认实现，记录结果并调整路线。

不能把“更符合某种架构形式”作为发布理由，也不能承诺所有场景的内存都
下降。最终发布以可复现的净收益、稳定性证据和目标平台结果为准。

架构约束见 [Memory ownership and rendering budgets](memory-ownership.md)，
现有工作负载见 [UI 性能测试矩阵](ui-performance-matrix.md)。
